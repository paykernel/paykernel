# Idempotency

Tap natively deduplicates `reference.idempotent` for 24 hours on **charges, authorizes, and refunds**. **Void is not Tap-idempotent.**

- **createPayment:** **requires** a caller `idempotencyKey`, sent as `reference.idempotent`. Omitted / blank throws `InvalidRequestError` before POST. The adapter does **not** mint a UUID. After create timeout / 5xx / Tap `1151` you have no `chg_…` or `auth_…` id — replay `createPayment` with the **same** key; do not `getPayment`.
- **capture / refund:** missing `idempotencyKey` throws `InvalidRequestError` before POST. These stay keyed: auto-retry (`withRetry`) is allowed because Tap deduplicates `reference.idempotent`. Capture of a `CAPTURED` authorize is **not** a POST replay: GET `CAPTURED` returns paid (omit `amount` without nested `charge_id`) and keeps `authorizationId`. `VOID` authorizes are not capturable. Refund of an already-`REFUNDED` charge maps the nested refund for this `idempotencyKey` (or `GET /refunds/{id}`). `REFUNDED` without a matching nested refund is `InvalidRequestError`, not a `POST` replay of `charge.amount`. A nested refund with a **different** `reference.idempotent` is not this refund.
- **void:** missing `idempotencyKey` throws `InvalidRequestError` before POST. The adapter GETs the authorize first: already `VOID` is a GET replay (`succeeded` + cancelled), not `POST /authorize/{id}/void`. The adapter may still send `reference.idempotent` on the void POST, but Tap does **not** deduplicate void. The adapter does **not** retry void after `afterProviderSubmit` (timeout / 5xx / unusable 2xx). Reconcile with `getPayment` instead of a second void POST. `getPayment` of an authorize VOID is `succeeded` + cancelled — reconcilers must **not** re-POST void. Charge VOID is a failed payment.
- Auto-retry (`withRetry`) runs only on GET or Tap-keyed mutations (charges / authorize / capture / refund). Caller-abort `NetworkError` after a mutating POST is **not** retried. Post-submit timeout / 5xx / empty-or-unusable 2xx body → `outcome: "indeterminate"`, never a forged `failed` or `InvalidRequestError`. Mutating 2xx with an `id` but no object `status` is the same (`indeterminate`), not Tap `UNKNOWN` / `failed`. HTML/proxy 5xx is mapped as mutating `NetworkError.afterProviderSubmit` (same as JSON 5xx), not a clean 503 and not a card decline. HTTP 50x is never Tap decline codes `501`–`516` (those are charge `response.code` values). Tap JSON error `1151` ("Gateway timed out") is also `NetworkError`; mutating 1151 is `afterProviderSubmit`. HTTP 5xx is classified before Tap JSON `1106` / other 11xx body codes.
