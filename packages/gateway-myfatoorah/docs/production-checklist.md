# Production checklist

- **Webhook secret:** configure `webhookSecret` (portal secure key) **separately** from `apiToken`. Never use the API token as the HMAC key. Verify before parse (`verifyWebhook`), then inbox-claim, then fulfill. Raw string webhook bodies are JSON-parsed before verify (MF-WEBHOOK-RAW).
- **Fulfill only `paid`:** never fulfill `requires_action` / `redirectUrl` results. Redirect return URLs are browser callbacks, not webhooks — confirm settlement with `GetPaymentStatus` / the signed webhook. `PaymentCompleted: true` without nested statuses is still `paid` (MF-PAYMENTCOMPLETED-REDIRECT); pending invoices stay `pending` even when transaction is `FAILED`/`AUTHORIZE`.
- **Hosts & tokens:** sandbox is `apitest.myfatoorah.com` (currency KWD, no real money). Live uses per-country hosts (`api`, `api-ae`, `api-sa`, `api-qa`, `api-eg`) and a per-country live token.
- **HTTPS callback:** `callbackUrl` and `webhookUrl` must be HTTPS. MyFatoorah rejects localhost.
- **No raw cards:** this backend adapter never sends cardholder data. Embedded sessions use `myfatoorahSessionId`; saved cards use `myfatoorahToken`. Never store PAN/CVC.
- **Idempotency:** always pass a caller `idempotencyKey` on create/refund **and provide `orderId`** (or `myfatoorahCustomer.reference`) for replay safety. Outside KWT/SAU that reference is **required**. On create timeout / 5xx / `afterProviderSubmit` / `indeterminate`, replay with the same key (250-minute cache **in KWT/SAU only** — https://docs.myfatoorah.com/docs/idempotency; **outside KWT/SAU `Idempotency-Key` is omitted** — create looks up `CustomerReference` and reuses only a **Paid** invoice whose amount+currency match; `Pending`, amount mismatch, inquiry `5xx`/non-404 `4xx`/empty success `Data` are `indeterminate` with the existing InvoiceId when known, not a second create; a `429` on the lookup is surfaced as `RateLimitError` with `Retry-After` so callers can back off — see [Charges](./charges.md#rate-limit-on-replay-lookup-i2)). Official 2xx not-found `Message` may create. Unkeyed create/`MakeRefund` `429` is not auto-retried (outside KWT/SAU). On refund submit-timeout, do **not** re-POST — reconcile with `GetRefundStatus` using the same `ExternalIdentifier`. Refund `Idempotency-Key` is KWT/SAU only; headerless retry is once, `retry: false`, and only when the error is “header not supported”. **250-minute expiry (I5):** after 250 min the same KWT/SAU `idempotencyKey` creates a new invoice — also pass a stable `orderId` (`Customer.Reference`) even in KWT/SAU and retain the key server-side until settlement; see [Charges](./charges.md#idempotency-window--250-minute-cache-i5) and [Idempotency](./idempotency.md).
- **Refund settlement & currency:** MakeRefund acceptance is not settlement. Wait for `REFUND_STATUS_CHANGED` `REFUNDED` (or `GetRefundStatus` `Refunded`) before treating a refund as complete. **MakeRefund amount is account base currency (e.g. KWD), not the currency you charged (e.g. SAR)** — sandbox (`live: false` → `apitest.myfatoorah.com`) base is always `KWD` regardless of `country`; live first-refund base is inferred from `country` (KWT→KWD, SAU→SAR, …) only when `live: true` and history is empty, otherwise `KWD` (MF-SANDBOX-BASE). Pass base explicitly on first refund when histories are empty; the adapter fails closed if you pass `SAR` after `BaseCurrency: KWD` is known.
- **Concurrent refunds (I6) — caller-side distributed lock required:** `ExternalIdentifier` is **not provider-deduped** and `GetRefundStatus`→`MakeRefund` has a TOCTOU window. Two parallel `refundPayment` calls with **different** `idempotencyKey` values for the same `InvoiceId` can both observe the same `remaining` and both `MakeRefund`, double-refunding outside KWT/SAU. KWT/SAU `Idempotency-Key` only dedupes the HTTP window, not `ExternalIdentifier`. **Require a caller-side distributed lock (e.g. Redis `SET NX` / DB advisory lock) per `InvoiceId` (or per `orderId`) for `refundPayment` outside KWT/SAU** — hold the lock across `GetRefundStatus`+`MakeRefund` and release after settlement. For the **same** key, the adapter's `GetRefundStatus` preflight (`ExternalIdentifier === idempotencyKey`) is crash-retry safe and prevents a second `MakeRefund`, but it does not protect concurrent different keys. See [Refunds](./refunds.md) and [Idempotency](./idempotency.md).
- **Pending `PaymentURL` recovery limit (I1):** `GetPaymentStatus` has no `PaymentURL` and `GET /v3/invoices/{id}` returns `"No invoices match this InvoiceId"` when there are no transactions (official — https://docs.myfatoorah.com/docs/get-payment-status). A pending invoice's redirect **cannot be recovered via inquiry**. Persist `PaymentURL` from `createPayment` **before ACK**. After a crash, query `GetPaymentStatus` for status but the redirect is lost — to let the customer pay, create a **new invoice with a new `orderId` / `CustomerReference` value** (new reference, not a replay of the same one). The adapter's pending `indeterminate` with `InvoiceId` lets you `getPayment` to observe status but will never mint a second chargeable invoice on the same reference. See [Charges](./charges.md#pending-paymenturl-recovery-limit-i1).
- **Amounts:** major units, ISO-padded on the wire (`10.50` SAR, `1.200` KWD). Zero amounts are rejected. `SR`→`SAR` aliased. Create `orderId` is sent as both `Order.ExternalIdentifier` and `Customer.Reference` (`Customer: { Reference = orderId }` or `myfatoorahCustomer.reference`; `customerId` is **not** `ExternalIdentifier` and does **not** become `Customer.Reference` — MF-CUSTOMER-REF) so webhooks carry it as `Invoice.ExternalIdentifier` → `paymentId`. See [Money](./money.md): create/`getPayment` publish **pay** when available, webhooks publish **base** (MF-WEBHOOK-MONEY-DRIFT).
