# Idempotency

- **createPayment:** **requires** a caller `idempotencyKey`, sent as the `Idempotency-Key` header **only in KWT/SAU** (https://docs.myfatoorah.com/docs/idempotency — header is omitted elsewhere to avoid a validation rejection). MyFatoorah caches the key for **250 minutes** — replay `createPayment` with the same key after timeout / 5xx / `indeterminate` in KWT/SAU. The adapter does **not** mint a UUID. Create is auto-retried (`withRetry`) when `KWT`/`SAU` (header dedupes, including `429`); KWT/SAU do **not** preflight `CustomerReference`. Outside KWT/SAU `orderId` or `myfatoorahCustomer.reference` is **required**, only connect-fail retries run (`429` after `/v3/payments` is **not** retried), and create **first looks up** that `CustomerReference` via `GetPaymentStatus` (`POST /v2/GetPaymentStatus` `KeyType: CustomerReference` — https://docs.myfatoorah.com/docs/get-payment-status and https://docs.myfatoorah.com/docs/payment-inquiry). Officially that key is **not unique** — only a **Paid** invoice whose pay/base amount matches the request amount+currency is reused (`MF-CREATE-REPLAY`). `Pending`, a Paid invoice with a different amount/currency, inquiry `5xx`, non-404 `4xx`, and `IsSuccess:true` with empty `Data` **fail closed** as `indeterminate` (no second `/v3/payments`). Fail-closed reuse of an existing invoice returns that **InvoiceId** as `gatewayId`. “No invoice yet” is HTTP **404** or HTTP **2xx** `IsSuccess:false` with empty `Data`, no `ValidationErrors`, and an official not-found `Message` (`No data matches this Key` / `not found` / `no invoice`). Generic `IsSuccess:false` does **not** create. A “header not supported” validation error retries once without the header; an idempotency **conflict** (same key, different body) does not.

  **250-minute expiry (I5):** After **250 minutes** (https://docs.myfatoorah.com/docs/idempotency) the same `Idempotency-Key` creates a **new invoice** even in KWT/SAU — the dedupe window has expired and KWT/SAU do not preflight `CustomerReference` today. For post-expiry safety **also pass a stable `orderId` (`Customer.Reference`) even in KWT/SAU** and **retain the `idempotencyKey` server-side until settlement** (`Paid` via webhook or `GetPaymentStatus`). Optional hardening (see `local://replay-proposal.md`): after expiry, if a `CustomerReference` lookup finds `Paid`+amount+currency match, reuse it even in KWT/SAU. At minimum, do not reuse an `orderId` for a new charge until the prior invoice is settled or you intentionally want a new invoice with a **new** `orderId`.

  **Rate-limit on lookup (I2):** The replay `GetPaymentStatus` itself is rate-limited (official warning on https://docs.myfatoorah.com/docs/get-payment-status). A `429` on that lookup is surfaced as `RateLimitError` (with `Retry-After`) so callers can back off and retry the same `orderId`/`idempotencyKey` without creating a second invoice. Other lookup failures remain `indeterminate`. See [Charges](./charges.md#rate-limit-on-replay-lookup-i2) and `local://replay-proposal.md`.

  **Pending URL cannot be recovered (I1):** `GetPaymentStatus` has no `PaymentURL` and `GET /v3/invoices/{id}` returns `"No invoices match this InvoiceId"` when there are no transactions (official). A pending invoice's redirect cannot be recovered via inquiry — persist `PaymentURL` before ACK; after a crash query status but the redirect is lost, so create a new `orderId` for a new invoice. The adapter's pending case returns `indeterminate` with the existing `InvoiceId` (no second create). See [Charges](./charges.md#pending-paymenturl-recovery-limit-i1).

- **refundPayment:** requires `idempotencyKey`, sent as `ExternalIdentifier` and (best-effort) the `Idempotency-Key` header **only in KWT/SAU**. A “header not supported” validation error retries **once** without the header (`retry: false` — no 429 fan-out). The **first** `MakeRefund` also does **not** auto-retry `429` (`isMyFatoorahRetryableBeforeSubmit` excludes `RateLimitError`). Conflicts are not retried. `ExternalIdentifier` still carries the key for replay. `MakeRefund` is **not** auto-retried after submit (`afterProviderSubmit`), because `ExternalIdentifier` does not dedupe on the gateway: reconcile via `GetRefundStatus` + the nested-refund key match instead of a second `POST` (preflight). **Any existing refund with `ExternalIdentifier === idempotencyKey` is returned before any `MakeRefund`, even for partial refunds (MF-CRIT-1).**

  **Concurrent refunds (I6):** `ExternalIdentifier` is **not provider-deduped** and the `GetRefundStatus`→`MakeRefund` sequence has a TOCTOU window. Two parallel `refundPayment` calls with different keys can each observe the same `remaining` and both `MakeRefund` (double-refund outside KWT/SAU). KWT/SAU `Idempotency-Key` only dedupes the HTTP window, not `ExternalIdentifier`. **Require a caller-side distributed lock per `InvoiceId` (or per `orderId`) for `refundPayment` outside KWT/SAU** — see [Production checklist](./production-checklist.md) and [Refunds](./refunds.md). The adapter's preflight `GetRefundStatus` by `ExternalIdentifier` prevents duplicate posting for the **same** key (crash-retry safe), but not concurrent different keys.

- Replay protection: a fully refunded invoice maps **only** the nested refund whose `ExternalIdentifier` exactly matches the key; otherwise it throws — never re-POSTs the invoice amount and never maps a single unkeyed refund to an unrelated key. Partial-refund replays with the same key also map to the existing refund before posting. Inquiry `POST`s (`GetPaymentStatus` / `GetRefundStatus`) are not money-mutating. `SR`→`SAR` aliased. Create outside KWT/SAU uses the `CustomerReference` lookup above instead of header dedupe.
