# Refunds

`refundPayment` requires `idempotencyKey` and `gatewayPaymentId` = the **InvoiceId** (digits) by default. Long (≥14 digit) ids look like a callback **PaymentId** and are rejected unless you pass `myfatoorahKeyType: "PaymentId"`. GetRefundStatus is always keyed by the resolved InvoiceId; MakeRefund then uses the caller key type (`InvoiceId` or `PaymentId`).

Flow:

1. `POST /v2/GetRefundStatus` (`KeyType: InvoiceId`) — official `Data.RefundStatusResult[]` (legacy `Refunds` still accepted). Each entry has `RefundId`, `RefundStatus`, `Amount`/`RefundAmount`, `BaseCurrency` (account base, e.g. KWD), `ExternalIdentifier`. A 2xx with `Data: null` (nullable per OpenAPI) **or** official 2xx `IsSuccess:false` not-found `Message` is an empty refund history. `ExternalIdentifier` is checked first for idempotency.
2. `POST /v2/GetPaymentStatus` — invoice value + currency (from `InvoiceTransactions`; official field is `InvoiceTransactions`, legacy `Transactions` fallback; `"KD"` alias → `"KWD"`). `InvoiceValue` is **base currency** per https://docs.myfatoorah.com/docs/get-payment-status (not pay/display). Picks the **last** success transaction for currency when needed. `getPayment` is **refund-blind** — after a full refund `GetPaymentStatus` still returns `Paid` (see `docs/status-mapping.md` I3); use `GetRefundStatus` / `REFUND_STATUS_CHANGED` to observe refunds.
3. `remaining = InvoiceValue − (Refunded/Pending refunds)`. Canceled refunds do not count. Negative or unparseable remaining **fails closed** (even with explicit `amount`); empty refund list → `remaining = InvoiceValue` (no refunds yet). Amounts compared via minor units to avoid IEEE error. **Before any `MakeRefund`, if any `RefundStatusResult` entry has `ExternalIdentifier` exactly equal to this `idempotencyKey`, that refund is returned immediately (idempotent partial-refund replay via `GetRefundStatus` preflight — MF-CREATE-REPLAY style `ExternalIdentifier` + `GetRefundStatus`) — `MakeRefund` is never re-POSTed, even when `remaining > 0`.**
4. Remaining `0` with no matching `ExternalIdentifier` → `InvalidRequestError` — never re-POST the invoice amount and never map a single unkeyed refund to an unrelated key. Lookup handles both `RefundStatusResult` and `Refunds` shapes.
5. `POST /v2/MakeRefund` with `ServiceChargeOnCustomer: false`, `Amount` (**account base currency**, not display/pay currency — e.g. KWD when you charged SAR per https://docs.myfatoorah.com/docs/get-payment-status), `ExternalIdentifier: idempotencyKey`, optional `Comment` (`myfatoorahComment` or trimmed `reason`, max 500 chars), `KeyType`/`Key` matching the caller (`InvoiceId` or `PaymentId`). `currency` must match the **base currency** (`RefundStatusResult[].BaseCurrency` when present; first refund with empty history — sandbox `live: false` base is always `KWD` regardless of `country`; live `live: true` infers base from `country` — KWT→KWD, SAU→SAR, … — otherwise `KWD` (MF-SANDBOX-BASE) — and a pay-currency `currency` value throws before `MakeRefund`) — mismatch throws.
MakeRefund acceptance is **never** settlement: the result is `pending` / `refund_pending`. Fulfill refunds only after a `REFUND_STATUS_CHANGED` webhook with `Refund.Status=REFUNDED` (or `GetRefundStatus` `Refunded`). `Idempotency-Key` header is only honored in KWT/SAU; a provider **header-not-supported** validation error retries **once** without the header (`retry: false` — no 429 fan-out). The first `MakeRefund` also does **not** auto-retry `429`. Conflicts such as “key already used with a different request” are not retried. `ExternalIdentifier` still carries the key for replay. See [Money](./money.md): refunds publish **base** currency (MF-WEBHOOK-MONEY-DRIFT); fixtures use KWD base + SAR pay.

## Concurrent refunds (I6) — `ExternalIdentifier` is not provider-deduped

`ExternalIdentifier` **does not dedupe on the gateway** and the `GetRefundStatus`→`MakeRefund` sequence has a TOCTOU window. Two parallel `refundPayment` calls with **different** `idempotencyKey` values for the same `InvoiceId` can both observe the same `remaining` and both `MakeRefund`, double-refunding outside KWT/SAU. KWT/SAU `Idempotency-Key` only dedupes the HTTP window, not `ExternalIdentifier`.

- **Require a caller-side distributed lock per `InvoiceId` (or per `orderId`) for `refundPayment` outside KWT/SAU** — hold the lock across `GetRefundStatus`+`GetPaymentStatus`+`MakeRefund` and release after settlement. Example: Redis `SET NX` with TTL, or DB advisory lock / unique job queue. See [Production checklist](./production-checklist.md) and [Idempotency](./idempotency.md).
- For the **same** `idempotencyKey`, the adapter's preflight `GetRefundStatus` (`ExternalIdentifier === idempotencyKey`) is crash-retry safe and prevents a second `MakeRefund` even when `remaining > 0` (MF-CRIT-1), but it does **not** protect concurrent different keys.
