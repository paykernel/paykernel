# Charges

`createPayment` (sale only) calls `POST /v3/payments`.

Required: `amount` (must be **> 0**), `currency` (3-letter), HTTPS `callbackUrl`, and a caller `idempotencyKey` (→ `Idempotency-Key` header **only in KWT/SAU** — https://docs.myfatoorah.com/docs/idempotency). Outside KWT/SAU, `orderId` or `myfatoorahCustomer.reference` is also required. Customer is otherwise optional.

Optional: `myfatoorahCustomer` ( `myfatoorahCustomer.reference` → `Customer.Reference`; else `orderId` → `Customer.Reference`), `myfatoorahPaymentMethod` (V3: `CARD` | `APPLE_PAY` | `GOOGLE_PAY` | `KNET` | `INVOICE`; default: config `defaultPaymentMethod`; both omitted → all enabled methods on the hosted page. Legacy V2 methods `BENEFIT`/`STC_PAY`/`MADA`/`QPAY`/`OMANNET` are `DisplayPaymentMethods` lowercase tokens, not `PaymentMethod`), `myfatoorahDisplayPaymentMethods` (lowercase tokens `card`, `knet`, `mada`, `benefit`, `stcpay`, `qpay`, `omannet`, …), `myfatoorahLanguage` (`EN` | `AR`), `myfatoorahWebhookUrl` (HTTPS), `myfatoorahSessionId` / `myfatoorahToken` (mutually exclusive → `SourceOfFund`), `orderId` → `Order.ExternalIdentifier` + `Customer.Reference` (both carry `orderId` so webhook `Invoice.ExternalIdentifier` → `paymentId` reliably; see `src/sources.ts` and `docs/webhooks.md`).

Never sent: `OperationType` (defaults PAY), `SaveCardOptions`, raw `SourceOfFund.Card` blobs (rejected before any fetch).

Response mapping:

- `PaymentCompleted: true` alone → `succeeded` / `paid` with no redirect even without nested `TransactionDetails.Invoice.Status=PAID` or `TransactionDetails.Transaction.Status=SUCCESS` (MF-PAYMENTCOMPLETED-REDIRECT). Nested PAID/SUCCESS without `PaymentCompleted: true` is **not** treated as paid (hosted create is `PaymentCompleted: false` + `PaymentURL`). Legacy `InvoiceStatus` is used only as `providerNativeStatus`. `PaymentURL` on a paid completion is the Result URL, not checkout — ignored when paid. Paid `Amount` is currency-aware: `ValueInPayCurrency` / `ValueInDisplayCurrency` / `ValueInBaseCurrency` is chosen to **match the request `currency`**; mismatched currency is omitted rather than published as the wrong amount (MF-CREATE-AMOUNT-FALLBACK). `InvoiceValue` in `GetPaymentStatus` is **base currency** per https://docs.myfatoorah.com/docs/get-payment-status (see `docs/money.md`); create/`getPayment` publish pay when available, webhooks publish base (MF-WEBHOOK-MONEY-DRIFT); `KD`/`SR` aliased to `KWD`/`SAR`.
- non-empty `PaymentURL` (hosted) when not paid → `requires_action` / `pending` + `redirectUrl`
- mutating 2xx with neither → `indeterminate` (`afterProviderSubmit`) — replay `createPayment` with the same `idempotencyKey`. **Idempotency-Key header is only sent in KWT/SAU** (https://docs.myfatoorah.com/docs/idempotency); outside those countries the header is omitted, `orderId` / `myfatoorahCustomer.reference` is required, and create first looks up that `CustomerReference` (not unique — official, returns the **last invoice** for that reference per https://docs.myfatoorah.com/docs/payment-inquiry and https://docs.myfatoorah.com/docs/get-payment-status) and reuses only a **Paid** invoice whose amount+currency match the request (MF-CREATE-REPLAY). `Pending`, `Refunded`/`PartiallyRefunded`, or a Paid invoice with a different amount/currency or missing amount **fails closed** as `indeterminate` with the existing `InvoiceId` when known (no second create) so callers can `getPayment` to observe status. **`Canceled`/`Failed` (including `Expired` → `failed`) for the same `CustomerReference` now **allows** a new `POST /v3/payments`** — a new invoice is created with the same reference (retry after cancel/failure); only `Pending`/`Refunded`/`PartiallyRefunded` and paid-mismatch block creation. See `src/gateway.ts` replay section and `GatewayFixer` change.

## Pending `PaymentURL` recovery limit (I1)

`GetPaymentStatus` **has no `PaymentURL`** and `GET /v3/invoices/{id}` returns `"No invoices match this InvoiceId"` when there are no `InvoiceTransactions` (official — https://docs.myfatoorah.com/docs/get-payment-status). A pending invoice's `PaymentURL` **cannot be recovered via inquiry**.

- The adapter's `MF-CREATE-REPLAY` pending case correctly returns `indeterminate` with the existing `InvoiceId` as `gatewayId` (so callers can `getPayment` to observe status) but **never creates a second chargeable invoice** on the same `CustomerReference`. The comment in `gateway.ts` create replay section documents this: `PaymentURL` is not retrievable via `GetPaymentStatus` or `GET /v3/invoices/{id}` when no transactions exist.
- **Persist `PaymentURL` before ACK.** After a crash, query `GetPaymentStatus` for status but the redirect is lost — to let the customer pay, **create a new invoice with a new `orderId` / `CustomerReference` value** (new reference, not a replay of the same one). Do not retry `createPayment` with the same reference expecting a recovered URL. See [Production checklist](./production-checklist.md).

## Rate-limit on replay lookup (I2)

The replay preflight `POST /v2/GetPaymentStatus` is itself rate-limited (official warning on https://docs.myfatoorah.com/docs/get-payment-status). The adapter surfaces a `429` on that lookup as **`RateLimitError` (with `retryAfterSeconds` from `Retry-After`)** instead of converting it to `NetworkError` `indeterminate`, so callers can back off and retry the same `orderId` / `idempotencyKey` without minting a second invoice. All other lookup failures (`5xx`, non-404 `4xx`, `IsSuccess:true` with empty `Data`) remain `indeterminate` with the existing `InvoiceId` when known — no second `POST /v3/payments`. A `429` on the money-mutating `POST /v3/payments` itself (outside KWT/SAU) is also surfaced as `RateLimitError` and is **not** auto-retried (`isMyFatoorahRetryableBeforeSubmit` excludes `RateLimitError`).

Proposal: `gateway.ts` catch distinguishes `RateLimitError` before the generic `NetworkError` indeterminate branch (see `local://replay-proposal.md` → Transport). Tests in `MF-CREATE-REPLAY` lock fail-closed for `Pending` / `Refunded` / amount mismatch / `5xx` / `400` / empty success `Data`; `Canceled`/`Failed` allow new invoice; an additional test asserts lookup `429` surfaces `RateLimitError`.

## Idempotency window — 250-minute cache (I5)

MyFatoorah caches `Idempotency-Key` for **250 minutes** (https://docs.myfatoorah.com/docs/idempotency) — replay `createPayment` with the same key in KWT/SAU is deduped within that window. **After 250 min the same `idempotencyKey` creates a new invoice even in KWT/SAU** (the header window has expired).

- KWT/SAU do **not** preflight `CustomerReference` by default (header dedupes). After expiry, a crash-retry with the same key would create a duplicate charge if callers rely solely on the header.
- **Recommend:** also pass a stable `orderId` (→ `Customer.Reference`) even in KWT/SAU and **retain the `idempotencyKey` server-side until settlement** (`Paid` via `PAYMENT_STATUS_CHANGED` webhook or `GetPaymentStatus`). For post-expiry safety, the optional hardening (best-effort, never blocks create) is to look up by `CustomerReference` and reuse a `Paid` invoice whose amount+currency match even in KWT/SAU (see `local://replay-proposal.md` — optional, docs are the required fix; KWT/SAU preflight reuses `Paid`+match, otherwise falls through to `POST` without blocking on `Pending`/mismatch/`5xx`/`429`). At minimum, do not reuse an `orderId` for a new charge until the prior invoice is settled or expired and you intentionally want a new invoice with a **new** `orderId`.

See [Idempotency](./idempotency.md) for the full matrix.

`getPayment` calls `POST /v2/GetPaymentStatus` (`KeyType` `InvoiceId` by default; `myfatoorahKeyType: "PaymentId"` for `PaymentId` lookups; `PaymentId` may be string or number). Long `gatewayPaymentId` (≥14 digits) with `InvoiceId` throws with a hint to use `PaymentId`. Uses `InvoiceTransactions` (official per https://docs.myfatoorah.com/docs/get-payment-status; `Transactions` legacy fallback; picks the **last** `SUCCESS`/`SUCCSS` transaction) and normalizes `KD`→`KWD` and `SR`→`SAR`. `InvoiceValue` is **base currency** per https://docs.myfatoorah.com/docs/get-payment-status (not pay) — see `docs/money.md` and `docs/status-mapping.md` I3 (refund-blind). Never use `GET /v3/invoices/{id}` for unpaid invoices — it returns "No invoices match this InvoiceId" when there are no transactions. A pending invoice stays `pending` even when the latest transaction failed or is `AUTHORIZE` (the customer can retry the same invoice; `AUTHORIZE` is not fulfilled until capture). Inquiry `POST`s are not money-mutating: `5xx` / empty / HTML on `GetPaymentStatus` / `GetRefundStatus` never becomes `afterProviderSubmit` / `indeterminate`. `TransactionDetails.Transaction.PaymentId` is also checked for `relatedIds.paymentId`.
