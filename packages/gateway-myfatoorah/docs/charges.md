# Charges

`createPayment` (sale only) calls `POST /v3/payments`.

Required: `amount` (must be **> 0**), `currency` (3-letter), HTTPS `callbackUrl`, and a caller `idempotencyKey` (→ `Idempotency-Key` header **only in KWT/SAU** — https://docs.myfatoorah.com/docs/idempotency). Outside KWT/SAU, `orderId` or `myfatoorahCustomer.reference` is also required. Customer is otherwise optional.

Optional: `myfatoorahCustomer` ( `myfatoorahCustomer.reference` → `Customer.Reference`; else `orderId` → `Customer.Reference`), `myfatoorahPaymentMethod` (V3: `CARD` | `APPLE_PAY` | `GOOGLE_PAY` | `KNET` | `INVOICE`; default: config `defaultPaymentMethod`; both omitted → all enabled methods on the hosted page. Legacy V2 methods `BENEFIT`/`STC_PAY`/`MADA`/`QPAY`/`OMANNET` are `DisplayPaymentMethods` lowercase tokens, not `PaymentMethod`), `myfatoorahDisplayPaymentMethods` (lowercase tokens `card`, `knet`, `mada`, `benefit`, `stcpay`, `qpay`, `omannet`, …), `myfatoorahLanguage` (`EN` | `AR`), `myfatoorahWebhookUrl` (HTTPS), `myfatoorahSessionId` / `myfatoorahToken` (mutually exclusive → `SourceOfFund`), `orderId` → `Order.ExternalIdentifier` + `Customer.Reference` (both, so `PAYMENT_STATUS_CHANGED` `Invoice.ExternalIdentifier` reliably carries `orderId`; `Customer` is `{ Reference = orderId }` when `orderId` set and `myfatoorahCustomer.reference` absent, otherwise `myfatoorahCustomer.reference` — MF-CUSTOMER-REF). `customerId` is **not** `Order.ExternalIdentifier` and does **not** become `Customer.Reference`.

Never sent: `OperationType` (defaults PAY), `SaveCardOptions`, raw `SourceOfFund.Card` blobs (rejected before any fetch).

Response mapping:

- `PaymentCompleted: true` alone → `succeeded` / `paid` with no redirect even without nested `TransactionDetails.Invoice.Status=PAID` or `TransactionDetails.Transaction.Status=SUCCESS` (MF-PAYMENTCOMPLETED-REDIRECT). Nested PAID/SUCCESS without `PaymentCompleted: true` is **not** treated as paid (hosted create is `PaymentCompleted: false` + `PaymentURL`). Legacy `InvoiceStatus` is used only as `providerNativeStatus`. `PaymentURL` on a paid completion is the Result URL, not checkout — ignored when paid. Paid `Amount` is currency-aware: `ValueInPayCurrency` / `ValueInDisplayCurrency` / `ValueInBaseCurrency` is chosen to **match the request `currency`**; mismatched currency is omitted rather than published as the wrong amount (MF-CREATE-AMOUNT-FALLBACK). When `PaymentCompleted: true` but no `ValueIn*` currency matches the request `currency` (e.g. base KWD present but request SAR), `amount`/`currency` are **omitted intentionally** to avoid KWD-as-SAR drift — `isPaidOutcome` remains `true` and `status: paid` even though `amount` is undefined. Merchants **must not fulfill on `amount === undefined`** or must re-query `getPayment` for the authoritative amount (I8 — see `isPaidOutcome` does not require amount).
- non-empty `PaymentURL` (hosted) when not paid → `requires_action` / `pending` + `redirectUrl`
- mutating 2xx with neither → `indeterminate` (`afterProviderSubmit`) — replay `createPayment` with the same `idempotencyKey`. **Idempotency-Key header is only sent in KWT/SAU** (https://docs.myfatoorah.com/docs/idempotency); outside those countries the header is omitted, `orderId` / `myfatoorahCustomer.reference` is required, and create first looks up that `CustomerReference` (not unique — official, returns the **last invoice** for that reference per https://docs.myfatoorah.com/docs/payment-inquiry and https://docs.myfatoorah.com/docs/get-payment-status) and reuses only a **Paid** invoice whose amount+currency match the request (MF-CREATE-REPLAY). `Pending` or a Paid invoice with a different amount/currency **fails closed** as `indeterminate` with that invoice’s **InvoiceId** as `gatewayId` (`GetPaymentStatus` has no `PaymentURL` — never a second create). Inquiry 5xx / non-404 4xx / `IsSuccess:true` + empty `Data` also return `indeterminate`. Create proceeds only on HTTP 404 or HTTP 2xx `IsSuccess:false` with empty `Data` and an official not-found `Message` (`No data matches this Key` / `not found` / `no invoice`). Outside KWT/SAU a `429` on `/v3/payments` is **not** retried. KWT/SAU skip this preflight (header dedupes). A “header not supported” validation error retries once without the header; a key **conflict** does not. `SR`→`SAR` and `KD`→`KWD` aliases are normalized. Official `PaidCurrencyValue` / `TransationValue` strings may include grouping commas (`12,345.000`) and are parsed.

## Pending `PaymentURL` recovery limit (I1)

`GetPaymentStatus` **has no `PaymentURL`** and `GET /v3/invoices/{id}` returns `"No invoices match this InvoiceId"` when there are no `InvoiceTransactions` (official — https://docs.myfatoorah.com/docs/get-payment-status). A pending invoice's `PaymentURL` **cannot be recovered via inquiry**.

- The adapter's `MF-CREATE-REPLAY` pending case correctly returns `indeterminate` with the existing `InvoiceId` as `gatewayId` (so callers can `getPayment` to observe status) but **never creates a second chargeable invoice** on the same `CustomerReference`. The comment in `gateway.ts` create replay section documents this: `PaymentURL` is not retrievable via `GetPaymentStatus` or `GET /v3/invoices/{id}` when no transactions exist.
- **Persist `PaymentURL` before ACK.** After a crash, query `GetPaymentStatus` for status but the redirect is lost — to let the customer pay, **create a new invoice with a new `orderId` / `CustomerReference` value** (new reference, not a replay of the same one). Do not retry `createPayment` with the same reference expecting a recovered URL. See [Production checklist](./production-checklist.md).

## Rate-limit on replay lookup (I2)

The replay preflight `POST /v2/GetPaymentStatus` is itself rate-limited (official warning on https://docs.myfatoorah.com/docs/get-payment-status). The adapter surfaces a `429` on that lookup as **`RateLimitError` (with `retryAfterSeconds` from `Retry-After`)** instead of converting it to `NetworkError` `indeterminate`, so callers can back off and retry the same `orderId` / `idempotencyKey` without minting a second invoice. All other lookup failures (`5xx`, non-404 `4xx`, `IsSuccess:true` with empty `Data`) remain `indeterminate` with the existing `InvoiceId` when known — no second `POST /v3/payments`. A `429` on the money-mutating `POST /v3/payments` itself (outside KWT/SAU) is also surfaced as `RateLimitError` and is **not** auto-retried (`isMyFatoorahRetryableBeforeSubmit` excludes `RateLimitError`). KWT/SAU `POST /v3/payments` with the `Idempotency-Key` header **is** retried on `429` because the header dedupes.

Proposal: `gateway.ts` catch distinguishes `RateLimitError` before the generic `NetworkError` indeterminate branch (see `local://replay-proposal.md` → Transport). Tests in `MF-CREATE-REPLAY` lock fail-closed for `Pending` / amount mismatch / `5xx` / `400` / empty success `Data`; an additional test asserts lookup `429` surfaces `RateLimitError`.

## Idempotency window — 250-minute cache (I5)

MyFatoorah caches `Idempotency-Key` for **250 minutes** (https://docs.myfatoorah.com/docs/idempotency) — replay `createPayment` with the same key in KWT/SAU is deduped within that window. **After 250 min the same `idempotencyKey` creates a new invoice even in KWT/SAU** (the header window has expired).

- KWT/SAU do **not** preflight `CustomerReference` (header dedupes). After expiry, a crash-retry with the same key would create a duplicate charge if callers rely solely on the header.
- **Recommend:** also pass a stable `orderId` (→ `Customer.Reference`) even in KWT/SAU and **retain the `idempotencyKey` server-side until settlement** (`Paid` via `PAYMENT_STATUS_CHANGED` webhook or `GetPaymentStatus`). For post-expiry safety, the optional hardening is to look up by `CustomerReference` and reuse a `Paid` invoice whose amount+currency match even in KWT/SAU (see `local://replay-proposal.md` — optional, docs are the required fix). At minimum, do not reuse an `orderId` for a new charge until the prior invoice is settled or expired and you intentionally want a new invoice with a **new** `orderId`.

See [Idempotency](./idempotency.md) for the full matrix.

`getPayment` calls `POST /v2/GetPaymentStatus` (`KeyType` `InvoiceId` by default; `myfatoorahKeyType: "PaymentId"` for `PaymentId` lookups; `PaymentId` may be string or number). Long `gatewayPaymentId` (≥14 digits) with `InvoiceId` throws with a hint to use `PaymentId`. Uses `InvoiceTransactions` (official per https://docs.myfatoorah.com/docs/get-payment-status; `Transactions` legacy fallback; picks the **last** `SUCCESS`/`SUCCSS` transaction) and normalizes `KD`→`KWD` and `SR`→`SAR`. Never use `GET /v3/invoices/{id}` for unpaid invoices — it returns "No invoices match this InvoiceId" when there are no transactions. A pending invoice stays `pending` even when the latest transaction failed or is `AUTHORIZE` (the customer can retry the same invoice; `AUTHORIZE` never becomes `paid` until capture is implemented). `InvoiceStatus=Paid` without a `SUCCESS`/`SUCCSS` transaction stays `pending` (official inquiry rule) — see [Status mapping](./status-mapping.md). Amount is **pay** when a `SUCCESS`/`SUCCSS` transaction exists: `PaidCurrency`+`PaidCurrencyValue` (or `TransationValue` typo fallback) if parseable, otherwise `InvoiceValue`+`Currency` (base) — never a mixed base-value + pay-currency pair (MF-GETPAYMENT-BASE-MIX). Pending / Paid-without-success omit amount. `create` paid amount uses the same pay-first, currency-matched `ValueIn*` fallback and omits on mismatch (MF-CREATE-AMOUNT-FALLBACK). Inquiry `POST`s are not money-mutating: 5xx / empty / HTML on `GetPaymentStatus` / `GetRefundStatus` never becomes `afterProviderSubmit` / `indeterminate`. `TransactionDetails.Transaction.PaymentId` is also checked for `relatedIds.paymentId`.
