# Charges

`createPayment` (sale only) calls `POST /v3/payments`.

Required: `amount` (must be **> 0**), `currency` (3-letter), HTTPS `callbackUrl`, and a caller `idempotencyKey` (→ `Idempotency-Key` header). Customer is optional.

Optional: `myfatoorahCustomer` ( `myfatoorahCustomer.reference` → `Customer.Reference`; else `orderId` → `Customer.Reference`), `myfatoorahPaymentMethod` (V3: `CARD` | `APPLE_PAY` | `GOOGLE_PAY` | `KNET` | `INVOICE`; default: config `defaultPaymentMethod`; both omitted → all enabled methods on the hosted page. Legacy V2 methods `BENEFIT`/`STC_PAY`/`MADA`/`QPAY`/`OMANNET` are `DisplayPaymentMethods` lowercase tokens, not `PaymentMethod`), `myfatoorahDisplayPaymentMethods` (lowercase tokens `card`, `knet`, `mada`, `benefit`, `stcpay`, `qpay`, `omannet`, …), `myfatoorahLanguage` (`EN` | `AR`), `myfatoorahWebhookUrl` (HTTPS), `myfatoorahSessionId` / `myfatoorahToken` (mutually exclusive → `SourceOfFund`), `orderId` → `Order.ExternalIdentifier` + `Customer.Reference` (both, so `PAYMENT_STATUS_CHANGED` `Invoice.ExternalIdentifier` reliably carries `orderId`; `Customer` is `{ Reference = orderId }` when `orderId` set and `myfatoorahCustomer.reference` absent, otherwise `myfatoorahCustomer.reference` — MF-CUSTOMER-REF). `customerId` is **not** `Order.ExternalIdentifier` and does **not** become `Customer.Reference`.

Never sent: `OperationType` (defaults PAY), `SaveCardOptions`, raw `SourceOfFund.Card` blobs (rejected before any fetch).

Response mapping:

- `PaymentCompleted: true` alone → `succeeded` / `paid` with no redirect even without nested `TransactionDetails.Invoice.Status=PAID` or `TransactionDetails.Transaction.Status=SUCCESS` (MF-PAYMENTCOMPLETED-REDIRECT). When nested statuses are present, `TransactionDetails.Invoice.Status=PAID` **or** `TransactionDetails.Transaction.Status` in `{SUCCESS,Succss}` (official V3) also → `succeeded` / `paid`. Legacy `InvoiceStatus` / `TransactionDetails.Status` fallbacks still accepted. `PaymentURL` on a paid completion is the Result URL, not checkout — ignored when paid (`PaymentCompleted: true` or otherwise). Paid `Amount` is currency-aware: `ValueInPayCurrency` / `ValueInDisplayCurrency` / `ValueInBaseCurrency` is chosen to **match the request `currency`**; mismatched currency is omitted rather than published as the wrong amount (MF-CREATE-AMOUNT-FALLBACK).
- non-empty `PaymentURL` (hosted) when not paid → `requires_action` / `pending` + `redirectUrl`
- mutating 2xx with neither → `indeterminate` (`afterProviderSubmit`) — replay `createPayment` with the same `idempotencyKey`. **Idempotency-Key header is only sent in KWT/SAU** (https://docs.myfatoorah.com/docs/idempotency); outside those countries the header is omitted to avoid a validation rejection, and a post-submit timeout / `afterProviderSubmit` / `indeterminate` does **not** re-POST blindly — it first looks up `CustomerReference = orderId` (or `myfatoorahCustomer.reference`) via `GetPaymentStatus` to map an existing **Paid** invoice and avoid double-charge (MF-CREATE-REPLAY) — `Pending` is not reused because `GetPaymentStatus` has no `PaymentURL` (would lose redirect). If a provider `Idempotency` validation rejection is still seen (e.g. 2xx `IsSuccess:false` `ValidationErrors`/`FieldsErrors` as string body), create and refund both retry once without the header (`ExternalIdentifier` still carries the key for refunds). `SR`→`SAR` and `KD`→`KWD` aliases are normalized. Outside KWT/SAU without `orderId`/`myfatoorahCustomer.reference` there is no CustomerReference dedupe — provide `orderId` to get replay safety.

`getPayment` calls `POST /v2/GetPaymentStatus` (`KeyType` `InvoiceId` by default; `myfatoorahKeyType: "PaymentId"` for `PaymentId` lookups; `PaymentId` may be string or number). Long `gatewayPaymentId` (≥14 digits) with `InvoiceId` throws with a hint to use `PaymentId`. Uses `InvoiceTransactions` (official per https://docs.myfatoorah.com/docs/get-payment-status; `Transactions` legacy fallback; picks the **last** `SUCCESS`/`SUCCSS` transaction) and normalizes `KD`→`KWD` and `SR`→`SAR`. Never use `GET /v3/invoices/{id}` for unpaid invoices — it returns "No invoices match this InvoiceId" when there are no transactions. A pending invoice stays `pending` even when the latest transaction failed or is `AUTHORIZE` (the customer can retry the same invoice; `AUTHORIZE` never becomes `paid` until capture is implemented) — see [Status mapping](./status-mapping.md). Amount is **pay** when available: `PaidCurrency`+`PaidCurrencyValue` (or `TransationValue` typo fallback) if parseable, otherwise `InvoiceValue`+`Currency` (base) — never a mixed base-value + pay-currency pair (MF-GETPAYMENT-BASE-MIX). `create` paid amount uses the same pay-first, currency-matched `ValueIn*` fallback and omits on mismatch (MF-CREATE-AMOUNT-FALLBACK). Inquiry `POST`s are not money-mutating: 5xx / empty / HTML on `GetPaymentStatus` / `GetRefundStatus` never becomes `afterProviderSubmit` / `indeterminate`. `TransactionDetails.Transaction.PaymentId` is also checked for `relatedIds.paymentId`.
